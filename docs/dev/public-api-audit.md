# Public API audit

Scope: every name in `pychef.__all__` at the base commit `9d39063` (93 names, unchanged
by this work) and the new `pychef.ops` module. **Provenance note:** this audit was
written *after* `pychef.ops` was added, not before; the baseline half of the table was
generated from the unmodified `pychef.__all__` and is verified by
`tests/test_public_api_compat.py`, which pins that list.

The tables are generated by `docs/_scripts/generate_api_audit.py`
(`uv run python docs/_scripts/generate_api_audit.py`). Columns:

* **Typed** – every parameter and the return value of the callable (for classes: of
  all public methods) carry an annotation. `n/a` for aliases and data classes.
* **Docstring** – the object has its own docstring (not inherited).
* **In docs** – the name appears in a hand-written `docs/*.rst` page, or its module
  is rendered with `automodule`.
* **Stability** – `existing` symbols are kept source-compatible; `new` symbols may still
  receive keyword-only additions before 1.0.

## Findings

1. **No removals or signature changes.** All baseline names remain exported.
2. **Implementation details exposed at top level.** `pychef.ExecutionContext`,
   `PolicyDecision`, `normalize_host`, `Operation`, `OperationRegistry`, `registry`
   and `json_safe` are exported although only advanced users need them. They are kept
   (removal would be breaking); the docs mark `ExecutionContext` as engine API.
3. **Duplicated logic (pre-existing).** `Pipeline.xor` uses `ctf.xor_bytes` while the
   `XOR` operation uses `operations.maths._bitwise`. `pychef.ops.xor` goes through the
   operation (so policy limits apply) but decodes keys with `ctf.decode_bytes`, the
   function `Pipeline.xor` uses, for every key type, so `key_format` semantics are identical
   (checked by a parity test).
4. **Hash helpers.** `ctf.md5/sha1/sha256/sha512/digest` already return lowercase hex
   `str`. `pychef.ops` wraps the same functions (adding type and input-limit checks)
   and returns the same format; there is no second implementation.
5. **Missing docstrings (fixed):** the `Pipeline` convenience methods and
   `ctf.md5/sha1/sha256/sha512`. Remaining `no` entries below are the one-line
   `ctf` pack/unpack helpers (`p8`, `u16le`, ...), documented collectively on
   `docs/ctf-tools.rst`, and two packet parsers.
6. **`pychef.__dir__` did not list lazily loaded submodules (fixed):** `ops` and
   `operations` are now listed.
7. **Import cycles.** None found: `pychef.ops -> engine (recipe, execution, registry)
   -> types`; `operations/*` never import `pychef.ops` or `pipeline`. `ctf` no longer
   imports the AES implementation at module import.
8. **Import cost.** See `docs/dev/library-dx-release-report.md` (13 instead of 18
   `pychef` modules after `import pychef`).
9. **Packaging.** `py.typed` is present in the wheel (`check-wheel-contents` and
   `tests/smoke_test.py` assert it). `__version__` falls back to `"0+unknown"` when the
   distribution metadata is absent (for example a bare source checkout on `PYTHONPATH`).
10. **Type aliases.** `Data` and `RecipeConfig` are aliases and therefore show as
    `n/a`; `Args` is importable from `pychef.types` but not from the top level.
11. **Pipeline typing.** `Pipeline` methods are fully annotated; stage values are
    `Any` by design because `apply()` accepts arbitrary callables. Making `Pipeline`
    generic was considered and rejected as a large, low-value change.
